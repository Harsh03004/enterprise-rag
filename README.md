# Enterprise RAG Platform

A document question-answering application with a FastAPI backend, React frontend, PostgreSQL/pgvector storage, Redis/Celery ingestion jobs, hybrid retrieval, reranking, and Gemini or Ollama generation.

## Run locally with Docker Compose

Set a strong `SECRET_KEY`, then start the stack:

```bash
export SECRET_KEY="replace-with-a-long-random-secret"
docker compose -f infrastructure/docker/docker-compose.yml up --build
```

The frontend is served at `http://localhost:5173`; the API is at `http://localhost:8000`. PostgreSQL is published on host port `5434` by default (`POSTGRES_HOST_PORT` overrides it); containers use PostgreSQL internally on port `5432`. Compose uses `CONTAINER_DATABASE_URL` when set, otherwise it builds an in-network URL for the `postgres` service. Keep a host-run Python `DATABASE_URL` such as `localhost:5434` separate; `localhost` inside the API/worker container refers to that container. Compose runs PostgreSQL, Redis, the API, worker, scheduler, and frontend. API and worker share the `uploaded_files` volume. Ollama runs on the host, not in Compose: the Compose default is `http://host.docker.internal:11434/v1`, while host-run Python commands default to `http://localhost:11434/v1`. Set `OLLAMA_BASE_URL` to a different OpenAI-compatible endpoint when needed. Select `LLM_PROVIDER=gemini` and provide `GEMINI_API_KEY` to use Gemini. `GEMINI_MODEL` and `OLLAMA_MODEL` select provider models.

To use a local Ollama model, pull the desired model separately and set `OLLAMA_MODEL` (for example, `qwen3:8b`). The Compose stack does not install or run Ollama itself. On a cold start, the API may take up to two minutes to load its embedding and reranking models before `/ready` returns successfully; follow backend logs during this startup.

## Ingestion

Supported uploads are PDF, DOCX, Markdown (`.md`), and plain text (`.txt`). PDFs use text extraction with OCR fallback; DOCX extraction includes paragraphs, tables, and OCR of embedded images. Website ingestion accepts public HTTP/HTTPS pages and extracts visible page text. Processing occurs asynchronously; document status is visible in the sidebar.

## Evaluation

The evaluation suite lives in `backend/evaluation/`:

- `corpus/` holds the benchmark documents: a redacted StuMeet project report
  (DOCX with OCR'd screenshots), an employee handbook (Markdown), an IT security
  policy (TXT) and a product specification with tables (PDF, generated by
  `build_corpus_pdf.py`).
- `dataset.json` holds the cases. Each answerable case lists the facts a correct
  answer must contain (with accepted phrasings), optional forbidden phrases for
  near-miss facts, and its supporting evidence as short verbatim quotes. Quotes
  are matched against chunk text, so labels survive re-chunking. Unanswerable
  cases set `"should_fallback": true`.

The runner ingests the corpus for a dedicated, login-disabled evaluation user
through the normal upload and processing code, then runs every case through the
same retrieval → rerank → generate → verify pipeline used by chat. Ingestion is
skipped while the corpus files and chunking/embedding settings are unchanged.

```bash
cd backend
mkdir -p evaluation_runs
RUN_STAMP="$(date -u +%Y%m%dT%H%M%SZ)"
set -o pipefail
uv run python -m app.evaluation.runner \
  --baseline evaluation/baselines/gemini-3.1-flash-lite.json \
  --output "evaluation_runs/evaluation_${RUN_STAMP}.json" \
  2>&1 | tee "evaluation_runs/evaluation_${RUN_STAMP}.txt"
```

### Running locally on a laptop

`scripts/run_evaluation.sh` runs the suite inside the Docker stack with hard
resource limits, so a long local run cannot freeze the machine:

```bash
scripts/run_evaluation.sh                                  # full suite
scripts/run_evaluation.sh --case orion-pro-price           # selected cases
EVAL_MEMORY=4g EVAL_CPUS=6 scripts/run_evaluation.sh       # adjust limits
```

It pauses the worker, scheduler and frontend for the duration (restarting them
afterwards, also on Ctrl+C), caps the runner's CPU, memory and torch threads,
rests `EVAL_PAUSE` seconds between cases, and resumes automatically: rerun the
same command after an interruption and finished cases are kept, as long as the
dataset, model and RAG settings are unchanged (`EVAL_FRESH=1` starts over).
Results go to `backend/evaluation_runs/local-<model>.json` plus a `.txt`
transcript. Ollama must be running on the host.

Useful options: `--case ID` (repeatable) runs selected cases only, `--resume`
continues an interrupted run from `--output`, `--reingest`
forces a fresh corpus ingest, `--provider`/`--model` override the LLM, and
`--no-record` skips storing the run for the admin dashboard. Omit `--baseline`
to skip the regression comparison; `--max-regression 0.05` sets the allowed drop.

Reported metrics, each averaged only over the cases it applies to:

| Metric | Meaning |
| --- | --- |
| `answer_accuracy` | Answerable cases answered with every required fact and no forbidden phrase |
| `fact_recall` | Share of required facts present in answers |
| `refusal_accuracy` | Unanswerable cases correctly refused |
| `false_refusal_rate` | Answerable cases the system refused (lower is better) |
| `retrieval_hit_rate`, `passage_recall`, `mrr` | Whether, how much and how early labelled evidence was retrieved |
| `citation_precision`, `citation_recall` | Cited sources that hold labelled evidence, and labelled sources that were cited |

Results also break down pass rates by category and count pipeline outcomes
(`answered`, `no_context`, `model_declined`, `grounding_failed`).

For a host-run evaluation, `OLLAMA_BASE_URL` defaults to `http://localhost:11434/v1`. If Ollama listens on another host address, first check that address with `curl -fsS http://OLLAMA_HOST:11434/v1/models`, then set `OLLAMA_BASE_URL=http://OLLAMA_HOST:11434/v1` for the evaluation process. A run with case-level provider connection errors is incomplete and must not be treated as a regression score.
